## 2. Components and runtime boundaries

- `apps/web`: one Astro SSR application on `@astrojs/cloudflare` (`output: "server"`, `session: false`, `nodejs_compat`), deployed as one Worker (`punyasitus-web`) that is the Cloudflare for SaaS fallback origin (ADR-0007, ADR-0009, DEC-036). Worker entry `src/worker/index.ts` wraps Astro's handler to: (0) pass HTTP DCV paths (`/.well-known/pki-validation/*`, `/.well-known/acme-challenge/*`) through untouched, (1) export `TenantStore` (SQLite Durable Object) and `VideoTranscoder` (Cloudflare Container), and (2) export Queue `queue()` and Cron `scheduled()` handlers. Admin/portal pages render on the server; interactive regions are React 19 islands using **`shadcn/ui` v4 preset `base-nova` (`@base-ui/react` only, `rsc: false`, Lucide icons)**, Tailwind v4 and TanStack Table. Public-site and marketing routes ship zero React by default (`<= 25 KiB` gzip JS budget). Mutations use JSON endpoints under `src/pages/api/` documented in `docs/api` OpenAPI (no Astro Actions; the M2 `/mcp` endpoint is a bearer-token transport over the same services).
- **Four host-isolated surfaces** (decided from the normalized `Host` header before any route, session or cache work):
  1. `punyasitus.com` (`www` -> 308 apex): platform marketing site, live pricing, public demo tenants, legal pages and cookieless funnel events (`REQ-087`).
  2. `app.punyasitus.com`: tenant dashboard (`/dashboard/{handle}`), agency portal (`/agency`, `REQ-083`), affiliate portal (`/affiliate`, `REQ-086`), `/auth`, `/account`, app APIs, and (M2) `/mcp`, `/oauth2/*`, `/.well-known/oauth-*`. Never renders a tenant public site or console routes.
  3. `console.punyasitus.com` (`DEC-035 C11`, `REQ-049`): superadmin console and `/api/console/**`, protected by its own `__Host-` cookie, Google email allowlist, mandatory TOTP and active `platform_operators` grant. Returns 404 on every other host.
  4. Verified tenant hosts (`<handle>.situsku.click` or active custom domain): tenant public site plus `POST /api/leads`, `POST /api/events`, and `POST /api/abuse-report` (`REQ-094`); every `/dashboard`, `/agency`, `/affiliate`, `/console`, `/auth` or `/mcp` prefix returns 404. Unknown/pending/purged hosts return 404.
- `packages/db`: Drizzle ORM SQLite schemas, migrations and repositories split cleanly into `packages/db/src/platform/**` (`PLATFORM_DB` D1 control plane) and `packages/db/src/tenant/**` (`TenantStore` per-tenant SQLite DO via the `D1Database`-compatible RPC adapter of `adsbook.id`). All DB imports are server-only and instantiated per request from `env`.
- `packages/auth`: Per-request Better Auth (`drizzleAdapter(..., { provider: "sqlite" })`, `advanced.database.joins: true`, `ipAddressHeaders: ["cf-connecting-ip"]`), Google OAuth primary + email/password fallback, Organization plugin, `twoFactor` TOTP, and `mcp` OAuth 2.1 provider.
- `packages/core`: runtime-neutral Zod schemas, OpenAPI generators, canonical section & offering models, money/IDR math, vehicle credit-estimate integer calculator, URL/WA helpers, `pdf-lib` receipt builder, and pure-JS MP4 box sanitizer. Zero secrets, provider clients or DB bindings in browser exports.
- Background work: Cloudflare Queues (`punyasitus-jobs`), Cron Triggers (`7 * * * *`), and per-tenant `TenantStore` hourly `alarm()` (housekeeping, expiry). Non-H.264 MOV/WebM video transcoding runs in the scale-to-zero `VideoTranscoder` Cloudflare Container (`ffmpeg`).
- `R2`: `punyasitus-media` (every tenant object prefixed `t/<tenantId>/...`) and `punyasitus-backup` (daily `PLATFORM_DB` logical export, 30-day lifecycle). Image variants are produced via the Cloudflare Images binding.

Private application code stays in server-only modules. A tenant ID or handle is a selector, never authorization. Public loaders expose only published public DTOs; never leads, members, tokens or control-plane records.

## 3. Tenant, domain, and cache contracts

Normalize hostnames through URL parsing and IDNA handling: lowercase, remove a final dot and valid port, reject malformed hosts and IP literals outside an explicit local fixture map. Never trust incoming X-Tenant-ID or X-Forwarded-Host from arbitrary clients. Configure the trusted proxy boundary. Unknown, unverified, deleted, or conflicting hosts return a real 404, not a redirect.

Decided (ADR-0006, ADR-0009, DEC-029, DEC-036 — `adsbook.id` pattern): Step 0 passes `/.well-known/pki-validation/*` and `/.well-known/acme-challenge/*` through untouched so pending custom hostnames can complete HTTP DCV SSL issuance/renewal. Every other tenant-host request performs an authoritative primary-key read of `PLATFORM_DB` (`tenant_hosts JOIN tenants`), never KV. An in-isolate memory cache of at most **5 seconds** is allowed for active hosts only; moving, suspending or purging a host marks the mapping revoked, bumps `cache_version`, and quarantines a moved hostname for **60 seconds**. `PLATFORM_DB` or `TenantStore` failure (or `recovery` migration state) returns `503` + `no-store` instead of serving stale or unverified content.

Tenant states (DEC-035 C5, `adsbook.id` lifecycle): `provisioning`, `trial` (7 days, `noindex, nofollow`, platform subdomain only), `active`, `grace` (H+1..H+3, site live, CMS editable), `locked` (H+4..H+7, **site still live and indexable**, CMS read-only except view/export/pay/sign-out), `suspended` (from H+8, unpaid trial expiry, or operator hold: public 503 "Situs dalam perbaikan" + `no-store` + `noindex`, payment/export recovery only), `recovery` (failed DO migration, 503), `purging` and `purged` (H+45 paid / Trial+30d never-paid, 404 tombstone). Effective trial/active/grace may serve only within their authoritative deadlines; section 17 owns the precedence and exact boundaries. Subscription billing is amended by section 16: confirmed payment can extend entitlement idempotently, while operator suspension remains manual. Expiry follows section 17 without relying on scheduler timeliness; no automatic debit is implied. Status checks also apply to admin mutations, anonymous forms and jobs. Committed revocations affect subsequent requests; already in-flight responses cannot be recalled.

Domain lifecycle: requested -> pending_verification -> pending_ssl -> active; failed and disabled are explicit states. Store separate provider hostname status, certificate status, DNS target observation, provider ID, last check and safe failure code. Activate only when ownership, certificate and routing target all pass. A CNAME alone is insufficient. Poll with bounded exponential retry and jitter; timeouts stay pending/failed, not active. Reconcile uncertain create/delete calls by provider ID/hostname before retrying. Global hostname uniqueness prevents two tenants claiming the same name. Reattachment requires fresh verification.

One primary domain per tenant (partial unique index); primary-domain switch is transactional and requires an active destination. Verified aliases redirect GET/HEAD to the primary using 308, preserving safe path/query. This host canonicalization is not the excluded content redirect engine. Disable external alias redirects for POST; forms originate on the canonical host. Slug changes of published resources keep the previous URL working through the bounded former-slug 308 in section 7.1; warn before saving a published slug.

Cache only successful anonymous published GET/HEAD responses after authoritative resolution. Key includes hostname, tenant ID, route, normalized supported query parameters, publication revision and theme version. Bypass for preview, cookies that imply personalization, form/API responses, authorization headers, errors and responses containing Set-Cookie. Unknown query parameters bypass cache. After Step 2 (`resolveTenant` from `PLATFORM_DB`) succeeds for an anonymous GET/HEAD on a serving tenant, read/write Cloudflare's Worker Cache API (`caches.default`) using the synthetic key `https://cache.punyasitus.com/t/<tenantId>/v<cacheVersion>/<host><path>` with a short TTL (`<= 60s`). Because `resolveTenant` runs first and every publish, status, theme or domain change increments `cache_version`, revocations and updates take effect immediately without bypassing tenant checks. Publication increments revision in the same transaction; old entries become unreachable. Versioned media assets are immutable.

### 3.3 Request routing order and state pages (REQ-002, REQ-003, REQ-005, DEC-041)

Source: `adsbook.id` `src/platform/gate.ts`, `host.ts`, `state-pages.ts` and spec `08-DOMAIN-ROUTING.md` section 7, read 2026-11-18. The order below is the contract for `apps/web/src/worker/index.ts` and middleware; nothing earlier in the list may depend on anything later.

1. **Certificate paths** (`/.well-known/acme-challenge/*`, `/.well-known/pki-validation/*`): pass through untouched, before any host or tenant work. `/.well-known/cf-custom-hostname-challenge/*` is deliberately **not** passed through; that pre-validation token is served by the customer's current origin, not by us.
2. **Normalize `Host`** from the request URL itself; `X-Forwarded-Host` and `X-Tenant-ID` are never read. A host that cannot be normalized gets the neutral 404.
3. **Exact platform allowlist** (`punyasitus.com`, `www.punyasitus.com`, `app.punyasitus.com`, `console.punyasitus.com`; extra hosts only from a local-development setting). Each platform host serves only its own routes (section 2); any other path on it is the neutral 404. A marketing path requested on `app.` or `console.` moves with one `301` to `punyasitus.com` (query kept); `www.punyasitus.com` moves with one `308` to the apex.
4. **SaaS zone apex and `www`** (`situsku.click`, `www.situsku.click`) are not stores: `301` to `punyasitus.com`. The labels `www`, `fallback`, `cname`, `app`, `console`, `admin`, `api` stay reserved handles.
5. **Platform-only routes on a tenant host** (`/dashboard`, `/agency`, `/affiliate`, `/console`, `/auth`, `/account`, `/mcp`, `/oauth2`, `/api/console`) return the neutral 404.
6. **Tenant resolution** from `PLATFORM_DB` (`tenant_hosts JOIN tenants`), then the state mapping below. A control-plane read failure is a `503` for that host, never a default tenant.
7. **Primary-host redirect** for GET/HEAD when a custom primary is active: `www.<root>` and `<handle>.situsku.click` send one `301` to the primary with path and query (UTMs and click ids kept). **Never moved:** `/api/*`, `/.well-known/*`, and on the platform subdomain the owner's way in. A broken custom DNS therefore cannot lock the owner out. Removing the custom domain moves the primary back to the subdomain and the redirect stops, so there is no loop. (PLAN section 3 says `308` for aliases; `adsbook.id` ships `301`. Decision: **`301`** for host canonicalization, **`308`** only for the same-site former-slug moves of section 7.1. O2O check, verified 2026-11-18 against Cloudflare `saas-customers/how-it-works`: with O2O the customer's zone settings run first and ours second, and Cloudflare marks the request with `cf-connecting-o2o: 1`; nothing in that page restricts redirect status codes, so the `301` is issued by our Worker the same way. Risk that remains: a redirect or cache rule in the customer's own zone runs before ours and can override or loop with our `301`; the Domains screen tells O2O customers not to add redirect rules for the connected hostname, and the HTTPS probe of section 3.1 detects a loop before the hostname becomes primary.)
8. **Service gate** (lifecycle of section 17), then the edge cache (`caches.default` after step 6), then render.

| Resolved condition | Status | Page | Headers |
|---|---|---|---|
| Unknown, pending, revoked, quarantined, `provisioning`, `purging`, `purged` host | `404` | neutral "Halaman tidak ditemukan", identical body for every unknown host so nothing reveals which hosts exist | `no-store`, `noindex, nofollow` |
| `suspended` (operator hold or unpaid) | `503` per DEC-035 C5 | "Situs dalam perbaikan" | `no-store`, `noindex`, `Retry-After` |
| `recovery` (failed schema migration) | `503` | "Sedang dalam pemeliharaan" | `no-store`, `noindex`, `Retry-After: 60` |
| Control plane or tenant store unavailable | `503` | "Layanan sedang tidak tersedia" | `no-store`, `noindex`, `Retry-After: 60` |
| `trial` | `200` | live site | `X-Robots-Tag: noindex, nofollow` |

State pages carry no tenant data and no platform link, set a restrictive CSP (`default-src 'none'`), and answer API paths with JSON `{ success: false, code }` instead of HTML. Platform responses that must never be indexed (`app.`, `console.`, `/auth`, `/account`, `/api/*`) carry `X-Robots-Tag: noindex, nofollow` while staying crawlable so the header is read; the tenant owner's recovery entry and admin prefixes are noindex too.

### 3.1 Custom-domain delivery details (REQ-043)

- Paid websites only (`DEC-035 C4`: trial websites cannot connect a custom domain). Owner (or agency admin) opens Settings > Domains > Connect domain, enters a hostname only, and sees its normalized value. Reject schemes, paths, credentials, wildcards, the SaaS zone name, platform hosts, hostnames `> 64` characters (Cloudflare SSL CN Error 1469), and malformed names. Use syntactic normalization and platform deny rules; do not use a guessed public-suffix regex to decide DNS authority.
- Keep the platform subdomain as a verified fallback. Custom domain and `www` are separate hostname records; never automatically claim both or request a wildcard certificate. Each hostname needs its own activation evidence.
- Display exact record type, name, value, purpose and current status returned by provider integration; support copy actions and a last-checked timestamp. Ownership TXT and certificate validation records are distinct. Never manufacture TXT tokens or hardcode the SaaS CNAME target from an example.
- Subdomains normally point by CNAME to the configured SaaS target. Apex setup must detect supported DNS flattening/ALIAS/ANAME or the selected Cloudflare apex capability during the provider gate. Do not tell users to create a standards-invalid apex CNAME, guess IP addresses, or change nameservers. Default onboarding connects `www.<domain>` as primary because apex proxying is not generally available below Cloudflare Enterprise and many Indonesian registrar DNS services lack flattening; the apex is optional and offered only when the customer's DNS supports flattening/ALIAS (otherwise the customer may set an apex-to-www redirect at their registrar). The UI states this before setup; do not claim apex works on every DNS provider/plan.
- Background reconciliation owns provider polling. Manual Recheck is rate-limited, not an unbounded API loop. Surface pending DNS, ownership verified, pending certificate, active, failed and disabled states separately. Provide safe recovery for wrong target, conflicting hostname and certificate timeout without exposing raw provider credentials/responses.
- **O2O & Remedies:** Create the custom hostname via API *before* the customer saves a proxied Cloudflare CNAME (avoids Error 1014); instruct Cloudflare customers to set SSL/TLS to `Full` or `Full (strict)` (Flexible causes redirect loops). Surface specific remedies for HTTP DCV blocked (`PATCH ssl.method = "txt"`), restrictive DNS `CAA` records, and `Blocked` zone holds.
- **HTTPS Tenant-Marker Probe & 7-Day Reaper:** Enable Make primary only after `status == "active"`, `ssl.status == "active"`, DNS matches `cname.situsku.click`, **and** an HTTPS probe to the hostname returns this tenant's signed marker. A daily Cron reaper `DELETE`s custom hostnames stuck in `pending`/`failed`/`moved` for `> 7` days so abandoned domains do not incur $0.10/month charges, and monitors `/custom_hostnames/quota`. The previous active primary becomes an alias; canonical/OG/sitemap switch atomically through a revision update. Concurrent changes use optimistic version checks. `www` and apex may redirect to each other only when both are independently verified.
- Limits and lock (REQ-065): at most 2 custom hostnames per website. One domain name per website: its www and/or apex (www.X with X), or a single subdomain without a counterpart. The owner may add, recheck and remove hostnames while none is active (fixing typos or wrong DNS). Once any custom hostname is active, the custom domain set is locked: the owner may still add the missing counterpart, remove a counterpart that has never become active, and switch primary to another active hostname, but cannot remove or replace an active hostname. The Domains screen shows "Domain terkunci. Untuk ganti domain, hubungi admin." with a WhatsApp/support link built from the platform sales number. A domain change is performed by a platform operator on `console.punyasitus.com/domains` (section 13) with a reason and audit, using the same removal and connect flows below.
- Removal (owner before activation, operator after) requires confirmation naming the hostname. In one local transaction, change a removed primary to the active platform fallback and disable routing; subsequent requests cannot serve the old tenant. Then enqueue idempotent provider deletion and cache cleanup. Show cleanup pending on timeout, retry without re-enabling routing, and retain the claim until provider cleanup is reconciled. Explain that customer DNS must be removed separately; the platform never edits third-party DNS without authorization.
- Reconnecting a released hostname performs fresh ownership and TLS verification. Negative tests include previous owner's stale cache, duplicate claims racing, another tenant's provider ID, expired verification, stale primary updates and deletion timeout. Live validation uses an explicitly authorized disposable hostname; mocks do not establish real certificate issuance.

### 3.2 CNAME Connect System: three modes chosen by the owner's situation (REQ-043, REQ-004, DEC-040)

Source: Cloudflare for SaaS docs read 2026-11-18 (`hostname-validation`, `pre-validation`, `zero-downtime-migration`, validate-certificates `http`/`txt`/`delegated-dcv`). Two separate validations exist and use different tokens: **hostname ownership** (`ownership_verification` / `ownership_verification_http`, drives `status`) and **certificate DCV** (`ssl.validation_records`, drives `ssl.status`). Production traffic is safe only when `status = active`, `ssl.status = active` **and** the DNS target points to `cname.situsku.click`. Only one `ssl.method` (`http`, `txt` or `email`) is accepted per create request. The Domains screen asks one question first, "Apakah situs di domain ini sudah live di tempat lain?", then selects a mode:

| Mode | When | `ssl.method` | Owner steps (Indonesian UI) | Downtime |
|---|---|---|---|---|
| **A. Domain baru** | No live site on the hostname | `http` (automatic) | 1) buat record `CNAME www -> cname.situsku.click`; 2) tunggu status aktif | Short TLS-pending window is acceptable because nothing is live; the UI says so before setup |
| **B. Pindahan, nol downtime** | A live site (for example WordPress) must keep serving until cutover | `txt` | Step 1 (both records can be added while the old site runs): ownership `TXT _cf-custom-hostname.<host>` **plus** certificate record, either the one-time **Delegated DCV** CNAME on `_acme-challenge.<host>` (recommended: one record, Cloudflare then auto-renews) or a TXT on `_acme-challenge.<host>` (fallback when the registrar blocks underscore CNAMEs). Step 2: wait until **both** `status` and `ssl.status` are `active`. Step 3: only then change the CNAME to `cname.situsku.click`. | None. Rollback is reverting the CNAME to the old target; the old origin is untouched |
| **C. Domain sudah di Cloudflare (O2O)** | Customer's own zone is proxied by Cloudflare | `http` | Pre-validation is **not supported** for O2O (docs). Create the hostname first, then the customer adds the proxied CNAME and sets SSL/TLS to `Full`/`Full (strict)` | Activation routes traffic immediately; the UI warns of a brief window |

Rules:
- **Gate the cutover.** In mode B the "Siap pindah" state and the CNAME instruction stay locked until both `status` and `ssl.status` are `active`. Skipping pre-issuance causes a TLS-error window until the certificate finishes issuing (Cloudflare docs); the platform never offers that path for a live site.
- **Never build tokens or targets by hand.** Delegation hostname, ownership token and DCV tokens are read from the provider API/dashboard values (`GET` after create, because `validation_records` can be empty for a few seconds). Delegated DCV fails if a conflicting `_acme-challenge` TXT already exists at the customer's DNS or in the customer's own Cloudflare zone; the UI detects and names that record and asks the owner to remove it first.
- **Clean-up.** Ownership TXT can be removed after the hostname is active; the Delegated DCV CNAME must stay for renewals. The UI says which is which.
- **Token expiry and retries (verified 2026-11-18, Cloudflare `validation-backoff-schedule`).** DCV tokens are issued by the certificate authority and expire: **Let's Encrypt 7 days, Google Trust Services 14 days, SSL.com 14 days**; tokens can also become invalid on a failed validation. Cloudflare retries automatically on `min(60 * 1.05^attempt seconds, 4 hours)`, so most checks happen on the first day. The UI shows the token age, warns at day 5 (shortest CA), re-fetches tokens after expiry, and its "Periksa sekarang" button sends a `PATCH` to the custom hostname with the current `ssl` settings, which Cloudflare documents as resetting the backoff and triggering an immediate attempt (rate-limited on our side).
- **Optional DNS hint.** A bounded server-side lookup of the hostname's nameservers may preselect mode C. It only chooses instructions and never authorizes anything.
- **Renewal watch.** A Cron check reads `ssl.status` and DNS target for every active hostname; when the CNAME no longer points to the target, a Delegated DCV CNAME was removed, or renewal fails, the owner (and agency payer) gets a notice with the exact fix before expiry. The existing 7-day reaper still removes stale pending hostnames.
- **Known limits shown before setup.** A hostname behind another CDN that hides its DNS cannot be validated (Cloudflare docs); CAA records can block issuance; apex needs flattening/ALIAS support; hostnames longer than 64 characters and trial websites are refused.
- **Staging zone (verified).** The fallback origin is a per-zone setting (`PUT /zones/{zone_id}/custom_hostnames/fallback_origin`, one `origin` value, which must be a proxied A/AAAA/CNAME record). Staging therefore uses its own SaaS zone with its own fallback origin; it never shares the production zone.
- **Tenant TLD.** Chosen before the first client, because changing it later breaks every trial URL.
- **Public Suffix List (verified, decision changed).** The PSL PRIVATE section exists for domains that issue subdomains to mutually untrusting parties, which fits `situsku.click`, but the maintainers state (wiki `guidelines`, read 2026-11-18) that projects not serving more than thousands of users are likely to be declined and that entries need at least two years of registration left. (A search excerpt of the wiki's `Third-Party-Diffusion` page also lists breaking login, registration or cookie functions as a refusal factor; that page was not read in full.) PunyaSitus therefore does **not** depend on the PSL for v1. Without it, a script on one `*.situsku.click` site (for example a tenant's GTM container) can set a cookie with `Domain=situsku.click` that the browser then sends to every other tenant subdomain (cookie tossing). Isolation is enforced in code instead: (a) our responses never set a cookie with a `Domain` attribute on `situsku.click` or a tenant host; platform cookies are host-only `__Host-` cookies on `app.`/`console.` of the separate registrable domain `punyasitus.com`; (b) the only cookie on tenant hosts, the consent choice, is named with the `__Host-` prefix, which browsers refuse to set when a `Domain` attribute is present, so a sibling subdomain cannot forge it; (c) tenant-host code reads no cookie other than that `__Host-` consent cookie and never uses cookies for authorization; (d) a test fails the build if any response on a tenant host sets `Domain=` or a consent cookie without the `__Host-` prefix. Custom domains are separate registrable domains and are not affected. A PSL submission is reconsidered once the tenant count reaches thousands, with a two-year registration in place.


## 4. Identity, roles, and isolation

Platform origins (`punyasitus.com`, `app.punyasitus.com`, `console.punyasitus.com`) and the tenant SaaS zone (`*.situsku.click`) use separate registrable domains so tenant GTM/scripts are cross-site to the platform. `app.punyasitus.com` and `console.punyasitus.com` use distinct host-only `__Host-` session cookies (`Secure`, `HttpOnly`, `Path=/`, no `Domain`) signed with separate secrets. Primary sign-in is **"Masuk dengan Google"** (`REQ-090`, email/password fallback); `console.punyasitus.com` requires Google allowlist + mandatory TOTP; `agency_admin` requires TOTP. Every cookie-authenticated state-changing admin request requires `Content-Type: application/json` and an Origin exactly equal to the admin origin, independent of SameSite; public POSTs follow the section 6 Origin policy. Astro's built-in checkOrigin uses Sec-Fetch-Site with an Origin fallback but runs only for unsafe requests with no content-type or a form/text content type (docs.astro.build configuration reference, retrieved 2026-11-14), so the JSON admin check lives in src/middleware/ (TASK-023 decides whether checkOrigin stays enabled after verifying it behind the proxy). Instantiate `betterAuth()` **per request** from `env.PLATFORM_DB` (`drizzleAdapter(..., { provider: "sqlite" })`, `advanced.database.joins: true`) — never cache a module-level instance across Worker requests (forbidden cross-request I/O) and never use Workers KV as `secondaryStorage` (eventual consistency and 60s minimum TTL). The interactive authorize/consent page stays cookie-authenticated with the exact admin Origin and CSRF protection. All of these return 404 on tenant hosts. Membership is rechecked on every tenant action, including every direct API request. Login/reset/invite errors avoid account enumeration. ### 7.2 Storage quota and upload limits (REQ-064)

- Quota per website counts **normalized stored source bytes** (images after <=2 MB normalization, videos after processing; DEC-035 C8): 1 GB (1,000,000,000 bytes) while paid, in grace or locked, and 100 MB (100,000,000 bytes) during trial. Derivatives (WebP variants, posters, OG images) and backups are platform overhead and not counted. Trashed media counts until permanently deleted; permanent deletion frees its bytes.
- Enforcement is atomic: the upload intent declares the source byte length (bounded by the per-kind upload cap: 5 MB raw / 2 MB normalized image, 10 MB video), locks tenant_storage_usage and reserves exactly that declared length, rejecting with 422 (code STORAGE_QUOTA_EXCEEDED, current usage and limit) if reserved + finalized + declared length would exceed the quota. The streaming byte counter aborts any body that exceeds its declared length. Finalize replaces the reservation with the normalized stored byte count (`<= 2 MB` for images, processed MP4 bytes for videos); responsive WebP variants, posters and backups are platform overhead and not counted. Expired or failed intents release their reservation in the cleanup job. Parallel uploads can never exceed the quota. Tests: 999,000,000 bytes used + a 1,000,000-byte image succeeds and reaches exactly 1 GB; one more byte fails; a remuxed video whose output differs from its source still counts the source size.
- Upload rate limit per website: 50 upload intents per rolling hour and 200 per day, returning 429 with Retry-After. This protects job CPU from upload spam regardless of remaining quota.
- When trial becomes paid the quota rises immediately. A tenant already above a lower quota keeps existing media but cannot upload until below it. Locked tenants cannot upload (section 17.4).
- Media library and upload controls show "Terpakai X MB dari Y" with a warning at 80%. Quota add-ons are not part of v1.
- Abuse such as spam or phishing images is handled by the terms of service and operator suspension (section 13), not by quota; uploads require an authenticated member and are audited.

## 14. Private Draft Preview (In-Process)

Decision (ADR-0007): draft and published HTML use the same registered Astro theme components inside the single web application. There is no internal renderer endpoint, service credential, signed request or nonce store.

### 17.4 Account emails, verification and password recovery (REQ-077, REQ-090, DEC-041)

Source: `adsbook.id` `seller-email.ts`, `signup-verification.ts`, `admin/recovery.ts`, `login.ts` read 2026-11-18. Owner approved: recovery in three layers, verification by code.

- **Sender (verified 2026-11-18, Cloudflare `email-service/configuration/send-bindings`).** `send_email` binding `EMAIL` restricted with `allowed_sender_addresses: ["noreply@notif.punyasitus.com"]`; a send from any other address fails with `E_SENDER_NOT_VERIFIED`, and the sender must belong to an onboarded Email Service domain. Recipients are intentionally **not** restricted (the binding must reach any customer); before the sending domain is onboarded, the binding can only reach verified destination addresses in the account, which is what staging uses. Mail is built behind the `EmailPort` transport so tests inject a sink.
- **No blind retry.** Cloudflare's `send()` documents no idempotency, so an ambiguous outcome is never replayed. Each transactional message type takes a **claim before sending** (unique key per tenant or account and message kind) and keeps it whatever the outcome. Outcomes are recorded as `submitted` (returned, not proof of delivery), `failed` (a Cloudflare `E_*` code or a malformed-argument `TypeError`, the call definitely refused), `unknown` (timeout or network error), `skipped` (no transport bound, nothing claimed) or `duplicate`. Logs hold only an id and a sanitized code, never the recipient or text. This **replaces** the "bounded retries" wording of REQ-077 for one-shot messages; reliable re-delivery needs a durable outbox and stays out of v1 except for payment receipts, which are re-sendable by the payer from the receipts list.
- **Email verification by 8-digit code.** Sent to the exact address; valid 10 minutes, single use, at most 5 attempts, at most 3 sends per address per hour with a 60-second gap, and a per-network ceiling. Only keyed digests are stored (the code bound to challenge id and email; HKDF-SHA-256 of a platform secret with its own `info` label), never the code, the address or the challenge id. The challenge is consumed in the same `PLATFORM_DB` batch that creates the account, so a wrong code creates nothing and two concurrent claims create exactly one. No secret configured means no code is issued (fail closed); there is no test bypass. The code is not in the subject line. Google sign-in with `email_verified: true` skips this step.
- **Password recovery, three layers.** (1) **Google users:** recover through Google; the platform stores no password for them. (2) **Email and password users:** a single-use reset link by email, hashed at rest, short expiry, same response whether or not the address exists, rate-limited per address and per network, with every session revoked on success. (3) **Locked-out owner:** a platform operator verifies the requester out of band against the signup record and issues a single-use recovery token, redeemed by the owner who sets a new password; the platform never sees or sets the password, the redemption is audited, and the token is spent atomically with its audit event so one token can never change a password twice. Layer 3 is the safety net, not the main path.
- **Login.** One door per surface. Every refusal (unknown identifier, wrong password, inactive account) reads the same and costs about the same work; failures are counted per (network address, identifier) pair so a guesser on one network cannot lock the owner out from another.

### 19.7 Frozen-Core Theme Store & Modular First-Party Plugin Architecture (`REQ-096` through `REQ-099`, `ADR-0010`, `DEC-037`)

- **Frozen Core Rule (Zero Core Churn for Bespoke Work):** `packages/core`, `packages/db`, `packages/auth` and `apps/web/src/core` never carry client-specific `if` branches or one-off tables. Client visual customizations ship as Themes (`apps/web/src/themes/{premium,custom}/<theme-id>`, `docs/themes/THEME-DEVELOPMENT.md`) and client functional requirements ship as First-Party Plugins (`packages/plugins/<plugin-id>`, `docs/plugins/PLUGIN-DEVELOPMENT.md`) on the single shared `punyasitus-web` Worker + per-tenant `TenantStore` DO (rather than deploying 1 Worker per regular client via Workers for Platforms, which disables `caches.default` and hits Client API rate limits on fleet updates).
- **Theme Style Variants & Commercial Theme Store (`REQ-096`):** Each of the 6 platform themes exposes `>= 4` curated **Style Variants** (WCAG AA palette, font pair `<= 1` custom font, radius/card density, header/hero layout variant) selectable in 1 click without losing content. `PLATFORM_DB` `theme_catalog` & `tenant_theme_entitlements` manage `included`, `paid_once` (AutoLaris QRIS/VA checkout, coupons, numbered PDF receipt, affiliate commission; agency-billed for agency clients), and `custom` themes.
- **Plugin Manifest & Five Isolated Extension Slots (`REQ-097`):**
  1. **Namespace-Locked `TenantStore` Tables:** Additive SQLite migrations in `_plugin_migrations` restricted strictly to `plg_<snake_id>__*` table names, run **only** on tenants that activate the plugin after recording a PITR bookmark in `PLATFORM_DB.migration_bookmarks`. Deactivation or expiry preserves `plg_*` data intact until `H+45` website purge.

## 20. Trust, Support and Retention Foundations (REQ-103 through REQ-110, DEC-043)

Sources and evidence labels are in `punyasitus-docs/docs/research/2026-11-18-gap-review.md` section F.

### 20.1 Shared-domain protection (REQ-103)

- **Why:** in August 2024 Kominfo blocked WordPress.com and Weebly because gambling sites hid in their subdomains (Reported, Katadata 2024-08-04). `adsbook.id` saw its seller zone land on the Trust+ IP list through a shared Cloudflare IP pair, and re-creating the zone did not change the IPs (Observed, `adsbook.id` runbook section 6).
- **Publish-time screening:** a server-side check on every publish and on MCP publishes. Inputs: title, rich text, links (resolved host), image ALT, custom-form labels. Rules: a versioned keyword and domain denylist in `PLATFORM_DB`, editable by operators. A match stores the item as draft with reason `held_for_review` and creates a queue row; the owner sees "Konten ditahan untuk ditinjau" without the matched term. False positives are released by an operator with audit.
- **Trust+ watch:** reuse the `adsbook.id` design. Once a day the platform cron resolves the platform hosts, `cname.<tenant zone>` and every active tenant host over DNS-over-HTTPS (A records; the list is IPv4) and compares them with the list published at `https://trustpositif.komdigi.go.id/assets/db/ipaddress_isp` (the URL `adsbook.id` uses; re-check before launch). A hit is logged on every run and notified once a day. When the list or DNS cannot be read, the result is "unknown", never "clean".
- **Takedown:** `console.punyasitus.com` action "Turunkan situs" sets an operator hold (REQ-005 suspended state) with reason and audit; public access ends on the next request after the cache version bump. Internal target: under 1 hour from report to takedown. Reported legal clock: Kepmen Komdigi 127 and 128 of 2026 treat gambling as urgent content, with a 1 x 12 hour reply to the pre-order notification and a 4-hour deadline once an order is issued (CNN Indonesia 2026-11-04; decree text not read, verify before writing an external SLA).
- **Blast radius:** a second tenant zone with its own Cloudflare for SaaS setup, fallback origin and checked IPs is kept ready. Moving trial subdomains to it is an operator runbook step, not an automatic switch. Paid clients on custom domains are unaffected by a tenant-zone block.
- **Normalisation runbook:** `docs/operations/trust-positif.md` holds the steps on `trustpositif.komdigi.go.id` (ownership statement, proof of purchase, statement that the site was cleaned; Observed, Jagoan Hosting guide) and the document set prepared in advance.

### 20.2 Help center and support (REQ-104, REQ-105)

- Help center pages live under `apps/web/src/pages/marketing/bantuan/**` as Astro content, so they cost nothing extra and follow the marketing site's SEO rules. A `help_slug` per dashboard screen maps the help icon to its article; a build check fails when a mapped article is missing.
- The help button builds `https://wa.me/<support number>?text=` with "Halo, saya butuh bantuan untuk situs {handle}, halaman {screen}." Support number, hours and response target are `platform_settings` values. Agency-managed websites show the agency contact from REQ-083 first.

### 20.3 Status page and staged releases (REQ-106)

- Status page: a separate static site on its own host (for example a Cloudflare Pages project), so it survives a platform Worker outage. Operators publish incidents there; the dashboard reads the current incident from `PLATFORM_DB` and shows a banner.
- Staged releases (Observed, Cloudflare docs "Gradual deployments", updated 2026-11-12): `wrangler versions upload` then `wrangler versions deploy` splits traffic between versions, with rollback. Rules for our Worker: only one Durable Object version runs at a time, so a release with a `TenantStore` schema change follows the bookmark-guarded migration of section 5.2 and is applied with `wrangler deploy`; version skew between requests of the same user is possible, so API changes stay backward compatible for one release; gradual deployments use only the last 100 uploaded versions.

### 20.4 Export and owner deletion (REQ-107)

- Export: a Queue job builds a ZIP in R2 under the tenant prefix (`t/<tenantId>/exports/`), stores pages, posts and offerings as JSON, leads as CSV, and copies media; the signed link expires after 24 hours; at most one export per website per day.
- Deletion: owner-only with recent second-factor or re-authentication; sets `deletion_requested_at`; the site goes offline at once with a neutral page; the owner can cancel for 7 days; after that the existing serialized purge runs. Billing and audit records follow their own retention.

### 20.5 QR code, AI onboarding and monthly report (REQ-108, REQ-109, REQ-110)

- QR: generated in the Worker with a small pure-JS encoder, SVG and PNG, for the canonical primary URL, optional `utm_source=qr`. No external service.
- AI onboarding: one optional step after the three onboarding answers; each generated field is a draft with the `CONTOH` marker; facts (prices, licences, reviews, addresses) are never generated; gated on the AI provider decision of DEC-028 and counted against its quota.
- Monthly report: a monthly cron enqueues one job per active website; data comes from the insights tables of REQ-073; minimum activity threshold before sending (Wix Studio uses 30 monthly sessions for its client reports, Observed; our threshold is set during the task); owner can opt out; no blind retry (DEC-041). Retention impact is a hypothesis to measure, not a claim.
